AI Food Kiosk FPGA Deep Dive

A complete FPGA request-matching system: host communication, a four-cycle trigger pipeline, and reusable hardware components.

Table of Contents

Project Goal

The goal of this project is to demonstrate how an FPGA can implement a fast, specialized approximation of a slower, more-general computation.

In our AI Food Kiosk, speech recognition converts customer requests into text, which is forwarded to both an LLM agent and an FPGA-based pattern matcher. The FPGA recognizes a small set of predefined requests and immediately returns programmed actions, while the LLM handles requests requiring more general reasoning.

The FPGA is intentionally much less capable than the LLM. Its pattern matching can produce false positives, making it unsuitable for taking real customer orders without additional safeguards. However, this simplified application demonstrates a useful architectural pattern: performing common, predictable operations in dedicated hardware while retaining a more capable software fallback.

Deep Dive Goals

This article focuses on three main topics:

  1. Engineering a complete system from zero. Starting with a Basys3 FPGA, a laptop, and a USB connection, I designed and implemented the communication protocols, hardware modules, and host software needed to build a working system.
  2. Latency-aware engineering. I identified the latency-critical operations, mapped them to parallel hardware, and measured the resulting latency and resource utilization.
  3. Building Reusable FPGA IPs. Rather than building application-specific RTL for every function, I developed and tested a library of reusable components for communication, streaming, buffering, and data processing.

Engineering from Zero

When starting an FPGA project from scratch, the first thing we have to build out is the communication between host and FPGA. I have a Basys3 FPGA with a USB connection on the J4 port. Per the Basys3 manual, user data over the J4 USB bridge is hardwired exclusively for UART.

UART Bitstream

UART is a protocol for transmitting bytes over a connection one bit at a time. Here is an example diagram of how UART transmits the bits 01101110 at 115,200 baud. 

  Time ------------------------------------------------------------------>

           Idle   Start   D0    D1    D2    D3    D4    D5    D6    D7   Stop
  Value      1      0      0     1     1     1     0     1     1     0     1

  HIGH   --------+           +-----------------+     +-----------+     +-------
                 |           |                 |     |           |     |
  LOW            +-----------+                 +-----+           +-----+
                    ^     ^     ^     ^     ^     ^     ^     ^     ^     ^
  RX samples:     Start   D0    D1    D2    D3    D4    D5    D6    D7   Stop

  Interval (us): |<--->|<--->|<--->|<--->|<--->|<--->|<--->|<--->|<--->|<--->|

                 |<--->|
                 8.68 us interval per bit, ^ indicates sampling near center of each interval

Both the sender and receiver agree to the same bit rate (a.k.a baud rate). At 115,200 baud, the sender holds each bit’s voltage for approximately 8.68us, or 868 cycles of the Basys3’s 100 MHz clock. The receiver detects the falling edge of the start bit, samples near its midpoint to validate it, and subsequently samples each data bit at one-bit intervals.

In our central FPGA library, we created fdk_uart_tx and fdk_uart_rx reusable IPs to handle the UART bitstream functionality.

Channel Framing

On top of the UART byte stream, we build a channel protocol. Each channel frame is 10 bytes. The first byte is a channel ID. The second byte contains descriptor bits, such as start-of-packet (SOP) and end-of-packet (EOP). The remaining 8 bytes are payload data. 

 Transmission order ---------------------------------------------->

  Byte      0          1          2       3              8       9
       +----------+------------+-------+-------+-----+-------+-------+
       |Channel ID| Descriptor |  D0   |  D1   | ... |  D6   |  D7   |
       +----------+------------+-------+-------+-----+-------+-------+
       |<-- Header: 2 bytes -->|<-------- Payload: 8 bytes --------->|

  Descriptor (byte 1):
       Bit   7    6    5    4    3    2    1    0
           +-----------------------------+----+----+
           |        Reserved (0)         |EOP |SOP |
           +-----------------------------+----+----+
struct [[gnu::packed]] ChannelFrame {
     static constexpr std::uint8_t SOP = 1 << 0;
     static constexpr std::uint8_t EOP = 1 << 1;

     std::uint8_t channel_id = 0;
     std::uint8_t descriptor = 0;
     std::byte payload[fdk::fpga::platform::CHANNEL_PAYLOAD_BYTES]{};
 };

If the overall message is not a perfect multiple of 8 bytes, the last frame will have unused bytes. It is up to the higher level protocol to encode enough information to identify these boundaries, such as with a msg_len field in a header.

I explicitly chose this 10-byte structure for two reasons:

  1. The logic is simple. You don’t have to track how many bytes you’ve received versus how many bytes you expect. Every chunk is always 10 bytes.
  2. A round-robin arbiter can mux 10-byte channel frames across channels in any order. This prevents any single channel with a large packet from hogging the entire bandwidth.

The tradeoff is the transmission overhead. For every 10 bytes of data on the wire, we only send 8 bytes payload data. We could improve this to 9 bytes of data for 8 bytes of payload by having only 64 channels and using the two freed up bits to indicate SOP/EOP.

Both the host and FPGA implement logic to aggregate payload data on a per-channel basis. On the FPGA, we implemented fdk_channel_rx and fdk_channel_tx reusable IPs to handle channel decoding. We also built a wrapper fdk_uart_channel_endpoint IP that deserializes uart_rx bits into rx channel data and serializes tx channel data into uart_tx bits.

Message Protocol

On top of the channel protocol, we built a straightforward message protocol. 

struct [[gnu::packed]] MsgHeader {
    std::uint16_t msg_size;
    std::uint32_t seq;
    std::uint32_t ack_seq;
    std::uint16_t msg_type;
};

template <typename T>
struct [[gnu::packed]] Message {
    MsgHeader msg_hdr;
    // Empty message bodies occupy no bytes in the wire format.
    [[no_unique_address]] T msg;
};

msg_size is the full length of the packet, including the header and the msg_size field. seq increases by msg_size for every packet. ack_seq is the last seq you received from the other endpoint. Finally, msg_type identifies the contents of the payload following this MsgHeader. The byte ordering for everything is little endian.

Senders and receivers can use seq and ack_seq to detect loss, however handling and recovering from data loss over a USB cable was not in scope for our MVP. Overall, the message protocol is designed such that if you were to produce a dump of data over a channel, you could reconstruct the sequence of messages.

We created fdk_message_rx and fdk_message_tx reusable IPs to handle message decoding for one specific channel.

The Admin Handler and Program Actions Handler form the control plane: they initialize the FPGA and configure conditions and reactions in the condition evaluator and reaction storage.

Once configured, the FPGA can process incoming stimuli and generate reactions without involving the host software in the decision-making process. The next section examines how the Stimulus Handler, Condition Evaluator, and Reaction Storage work together to minimize the number of clock cycles in the latency-critical path between detecting a match and emitting a reaction.

Latency Aware Engineering

The FPGA’s latency-critical path begins when the Stimulus Handler receives the input beat that completes a trigger condition, and ends when the first beat of the corresponding reaction is emitted.

Stimulus and Reaction Wire Format

Stimuli have the following format: 

__extension__ struct [[gnu::packed]] Stimulus {
    std::byte preamble[7] = {
        std::byte{0xaa}, std::byte{0xaa}, std::byte{0xaa}, std::byte{0xaa},
        std::byte{0xaa}, std::byte{0xaa}, std::byte{0xaa}
    };
    std::byte start_frame_delimiter = std::byte{0xab};
    std::uint64_t request_id;
    std::uint16_t length;
    std::byte payload[];
};

and reactions have the following format: 

__extension__ struct [[gnu::packed]] Reaction {
    std::byte preamble[7] = {
        std::byte{0xaa}, std::byte{0xaa}, std::byte{0xaa}, std::byte{0xaa},
        std::byte{0xaa}, std::byte{0xaa}, std::byte{0xaa}
    };
    std::byte start_frame_delimiter = std::byte{0xab};
    std::uint64_t request_id;
    std::uint8_t trigger_condition_id;
    std::uint8_t reaction_len;
    std::byte payload[];
};

These packets are sent on the Trigger channel, which does not use the MessageHeader protocol discussed earlier. Instead, we require receivers to parse the packet length out of the data stream and track bytes received to keep the problem similar to parsing Ethernet, IP, and TCP packets.

Important Fast Path Considerations

Here are two key considerations of our fast path to take note of:

Property 1: Process Data As Fast As It Comes In

In an Ethernet setup (often 10G), if you can’t keep up with the data rate, you will drop data. Even if you add buffers, sustained bursts can overrun it.

Our fast path accepts data as soon as it comes in, does not backpressure or buffer, and uses pipelined stages to split a complex process into smaller synthesizable pieces.

Property 2: Minimize Cycles Between Match and Fire

Define the start cycle to be the cycle on which the stimulus handler receives the beat that matches the trigger condition.

Define the stop cycle to be the first byte of the outbound Reaction message.

We want to minimize the value of stop - start .

Stage 1: Stimulus Handler

Now, let’s dive into the first stage of our fast path: the stimulus handler. The stimulus handler extracts payload beats from the main Stimulus message. It scans for the preamble and SFD, extracts the request_id and length fields, and feeds the next length bytes plus SOP and EOP framing into our condition evaluator component.

In all, Stimulus Handler processing takes one cycle.

Stage 2: Condition Evaluator

The condition evaluator takes an input beat from the stimulus handler and feeds it to MAX_CONDITIONS instances of our fdk_fast_string_contains algorithm. Each fdk_fast_string_contains algorithm processes the entire input beat combinationally in the same cycle.

fdk_fast_string_contains Algorithm

The fdk_fast_string_contains algorithm deserves a detailed walkthrough.

At a high level, we keep a window of the last MAX_PATTERN_LEN + CHARS_PER_BEAT characters. Then we check if the MAX_PATTERN_LEN characters ending at each of the CHARS_PER_BEAT characters in the latest beat perfectly matches the pattern. This combinational comparison performs CHARS_PER_BEAT equality comparisons across MAX_PATTERN_LEN bytes. It is resource-intensive, but completes within the same cycle. This parallelism reduces processing latency at the expense of hardware resources

Let’s walk through an example now. Suppose we have 2 bytes per beat, maximum pattern length 4, and the pattern we’re trying to match is “ABC”.

Preparing the Pattern

In the slow path, we create a right-aligned pattern. If the pattern is shorter than MAX_PATTERN_LEN, we will have leading 0 bytes that mean anything is allowed to match this character. This right-aligned, leading-0-byte pattern is necessary to allow us to compare against fixed window sizes regardless of the pattern length. The library fdk_fast_string_contains_pattern_preparer helper module abstracts out this pattern preparation logic.

From the right-aligned pattern, we produce a mask to identify which bytes matter and which bytes don’t. Later on, this mask will be used in byte_matches[i] = (mask[i]) || (window_slice[i] == pattern[i]) . 

Pattern:       [ 0 ][ A ][ B ][ C ]
Wildcard mask: [ 1 ][ 0 ][ 0 ][ 0 ]
                 |
                 +-- Ignore this byte during comparison

Effective pattern: [ * ][ A ][ B ][ C ]

Outputting to Reaction Storage

The fdk_fast_string_contains algorithm is combinationally expensive, so we have to register their outputs to meet timing. Each algorithm instance writes whether it matches or not to a condition_matches_ff[i] register.

In the next cycle, if a condition_matches_ff[i] register was set to high, the condition evaluator issues a load to the Reaction Storage for that condition’s associated reaction ID.

If multiple condition_matches_ff[i] registers are set to high, only the lowest indexed one is eligible to fire. Furthermore, once a condition fires, no conditions are allowed to fire anymore until we reach EOP and the next stimulus payload starts.

In all, Condition Evaluator processing takes two cycles.

Stage 3: Reaction Storage

Reaction Storage stores its reactions in a contiguous region of BRAM. Each reaction occupies a fixed-size slot of 32 eight-byte beats, giving us 256 beats of storage across eight reactions.

The BRAM is organized as a one-dimensional array of fixed-width beats. We calculate the starting address of each reaction as reaction_id * BEATS_PER_REACTION and stream successive beats until reaching the reaction's configured length.

Our RAM declaration is 

(* ram_style = "block" *) logic [BEAT_WIDTH-1:0] data [0:RAM_DEPTH-1];

where RAM_DEPTH is computed as 8 reactions * 32 beats per reaction = 256 beats.

To load a reaction, the caller provides the reaction_id and we go straight to data[reaction_id * BEATS_PER_REACTION] and start streaming out the beats up to the preconfigured length of the reaction.

When the condition evaluator provides the address of the reaction to output, the reaction storage directly streams the first beat’s BRAM memory to the output register in 1 cycle. Each subsequent beat is available by the subsequent cycle, so we never have gaps except when the downstream consumer backpressures.

Additional Latency Reductions

Here is our overall latency breakdown:

Trigger processing latency by pipeline stage
Stimulus Handler 1 cycle
Condition Evaluator 2 cycles
Reaction Storage 1 cycle
Total 4 cycles

There are also potential optimizations to further reduce the MVP’s 4 cycle latency.

Pre-sending the Constant Preamble

Since the first eight bytes of every reaction consist of the same preamble and start-frame delimiter, we could transmit this constant first beat as soon as a reaction is triggered, while the reaction table fetches the subsequent data. This would reduce the latency from four cycles to three cycles.

Advanced Optimizations

Further advanced optimizations could reduce the fastpath latency to 1 or 2 cycles, at the cost of additional complexity. These optimizations are nuanced and better deferred for an in-person discussion.

Measuring the Latency

We confirm the latency in cocotb using a test_stimulus_to_first_response_latency test case that asserts the latency is 4 cycles. This latency measurement assumes the downstream output interface is ready to accept the reaction immediately and excludes transport delays.

In a production system, we could also add a Trigger Metadata channel for independently measuring FPGA processing latency.

For each stimulus, the FPGA would emit a StimulusMetadata message containing its request_id and the cycle counter recorded when the Stimulus Handler forwards the first payload beat. Similarly, a ReactionMetadata message would contain the request_id and the cycle counter recorded when Reaction Storage emits the first reaction beat.

The host could correlate these timestamps by request_id and account for the position of the input beat that completed the trigger condition. For a continuous input stream, this is simply an offset based on the number of beats processed. For inputs containing gaps between beats, the host would need to account for the actual arrival timing.

This would provide an independent way to measure FPGA processing latency outside cocotb.

Throughput

We’ve discussed latency in great depth, so it’s now a good time to cover throughput.

Both the Stimulus Handler and Condition Evaluator are capable of processing one input beat per clock cycle. Consequently, neither component introduces an additional throughput bottleneck relative to our UART transport.

The reaction storage also sends an entire beat per cycle without any delays. On the transmit side of the triggering processing, we are also fully bound to the transport’s throughput.

One notable behavior though is our choice to drop reaction outputs if something is already serializing. This is chosen for simplicity so that we do not have to manage buffering in output queues.

This is also a practical choice. We have the restriction that a single stimulus can only trigger a single reaction. Given the Whisper speech-to-text model needs several seconds to convert an entire audio dialogue before a stimulus can be generated, it is highly unlikely two stimuli could arrive close to each other. So the scenario of multiple stimuli causing triggers to fire multiple reactions is extremely unlikely.

In the future, if handling multiple reaction outputs became important, it would be straightforward to add a buffer; however, if this buffer gets exhausted, we would still end up with drops.

Building Reusable FPGA IPs

Beyond optimizing latency and throughput, I also designed many of the building blocks as reusable library IPs. These include various types of arbiters and FIFOs, a streaming array-based table, and the UART, channel, and message protocol components discussed in the "Engineering from Zero" section.

These components are parameterized to support different data widths, beat sizes, and buffer depths. Rather than coupling them to the food kiosk application, I designed them with generic streaming interfaces so they could be composed into other FPGA projects.

Each component also comes with independent cocotb tests covering multiple parameter configurations. This allows me to validate the reusable infrastructure separately from the application logic and build future projects on an established, tested foundation.

C++ Testing Design

This article explains how GPU Store uses declarative service configuration, reusable test helpers, and Catch2 sections to keep tests focused and easy to follow.

Table of Contents

Design for Testability

All my microservices are designed with testability in mind.

Every service exposes a public api library defining the Config struct needed to instantiate it. Configurations use simple values such as strings, integers, and booleans, or compose configurations of other services. They avoid dependencies that are difficult to construct in a test. The one exception is the transaction database, which also accepts a StorageInterface to abstract disk writes. This makes service configuration straightforward to express inline.

Here’s an example of creating a Gateway service inline in a test: 

SessionConfig sess0_cfg{  
    .session_name = "sess0",  
    .password = "password0",  
    .company_id = funx::CompanyId{1},  
    .port = funx::TcpPort{20000},  
};  
SessionConfig sess1_cfg{  
    .session_name = "sess1",  
    .password = "password1",  
    .company_id = funx::CompanyId{1},  
    .port = funx::TcpPort{20001},  
};  
GatewayConfig cfg{  
    .unique_id = 0,  
    .server_ip4 = "127.0.0.1",  
    .matching_services = { matching_service.getMatchingServiceConfig() },  
    .sessions = {sess0_cfg, sess1_cfg},  
};

Gateway gateway(cfg);

Testing becomes much cleaner when you can instantiate components with just a few lines of declarative configuration.

Reusable Test Helpers

Services used in other services’ tests expose reusable setup helpers through a public test library. The helpers are defined in mock.h and keep repeated service setup out of individual tests.

For example, the gateway tests start a matching service using the following helper: 

TEST_CASE("Test Gateway One Matching Service", "[gateway]")  
{  
    funx::match::test::RunMockMatchingService matching_service;  
    ...  
    GatewayConfig cfg{  
        ...  
        .matching_services = { matching_service.getMatchingServiceConfig() },  
    };
}

The RunMockMatchingService helper adds a few test products and runs the matching service in a background thread for up to five seconds. It exposes the associated MatchingService::Config, making it easy to configure a Gateway to communicate with it.

Catch2 Testing Framework

I chose Catch2 because its sections and generators make shared setup and input variations easy to express within a test case. This suits the service tests shown below.

Sections

Catch2 lets you structure tests with sections that share setup and teardown code. The following excerpt checks that the Gateway rejects invalid order fields with the expected rejection reason. Some setup code is omitted for brevity. 

TEST_CASE("Test Gateway One Matching Service", "[gateway]")  
{  
    funx::match::test::RunMockMatchingService matching_service;  
    ...  
    Gateway gateway(cfg);  
    ...  
    GatewayTestClient sess0(Client::Config{  
        .gateway_cfg = cfg,  
        .session_cfg = cfg.sessions[0],  
    });

    SECTION("Send order and get reject") {  
        flop::NewOrder new_order{  
            .product = 1,  
            .side = flop::Side::Sell,  
            .qty = 123,  
            .price = 456,  
            .duration = flop::Duration::Day,  
            .client_order_id = 1234567,  
        };

        auto sendAndExpectReject = [&](flop::Reason reason) {  
            sess0.client().sendBasicNewOrder(new_order);  
            auto reject = sess0.requireResponse<flop::OrderReject>();  
            REQUIRE(reject.reason == reason);  
        };

        SECTION("Bad product") {  
            new_order.product = 843578;  
            sendAndExpectReject(flop::Reason::InvalidProduct);  
        }

        SECTION("Bad Side") {  
            new_order.side = static_cast<flop::Side>(255);  
            sendAndExpectReject(flop::Reason::InvalidSide);  
        }

        SECTION("Bad quantity") {  
            new_order.qty = GENERATE(-100, 0);  
            sendAndExpectReject(flop::Reason::InvalidQuantity);  
        }

        SECTION("Bad Duration") {  
            new_order.duration = static_cast<flop::Duration>(255);  
            sendAndExpectReject(flop::Reason::InvalidDuration);  
        }
    }
}

For each leaf section, Catch2 reruns the test case from the beginning, constructing a fresh matching service, gateway, and test client. This keeps their local state separate between runs; shared resources such as ports and files still require proper cleanup. Each rejection section contains only the two lines relevant to the behavior being tested.

The SECTION macro keeps shared setup alongside the scenarios that use it, so the reader can see how each test is configured without navigating to a separate fixture definition.

Furthermore, every section can add to what the previous scope defined. For example, the “Test Gateway One Matching Service” scope creates the matching service, gateway, and client. The “Send order and get reject” section adds a new_order variable that will be used in all the reject tests. This same new_order variable is not visible to any tests outside the “Send order and get reject” scope. I find this keeps shared setup and scenario-specific state easier to follow than spreading them across separate fixture definitions.

GENERATE Macro

Catch2 generators provide a concise way to run the same scenario across multiple input values. In the prior code snippet, we had 

SECTION("Bad quantity") {  
    new_order.qty = GENERATE(-100, 0);  
    sendAndExpectReject(flop::Reason::InvalidQuantity);  
}

Catch2 runs this section with qty = -100 and again with qty = 0, checking that both inputs receive InvalidQuantity. GENERATE keeps these input variations compact and lets the framework drive the repeated test execution.

Overall Testing Goals

My testing goals are to catch regressions and verify expected behavior, including invalid inputs and boundary cases. Tests also need to remain readable and maintainable as the system evolves. Designing components for straightforward setup and keeping each test focused makes failures easier to understand and investigate.

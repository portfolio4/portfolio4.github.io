C++ Testing Best Practices

In this article, I will point out important details in my C++ testing code that lead to high-quality, readable, and maintainable code.

Table of Contents

Design for Testability

All my microservices are designed with testability in mind.

Every service exposes a public api library that defines the Config struct needed to instantiate the service. Each Config struct composes either basic types or configs of other services. Basic types are “trivial” types like strings, integers, and booleans. Config structs don’t take pointers, references, or complex types that are difficult to instantiate. (The sole exception is the transaction database Config takes a StorageInterface that abstracts out writing to disk.) Thus, you can always declaratively instantiate a Config object inline using dummy primitive values.

Here’s an example of creating a Gateway service inline in a test: 

SessionConfig sess0_cfg{  
    .session_name = "sess0",  
    .password = "password0",  
    .company_id = funx::CompanyId{1},  
    .port = funx::TcpPort{20000},  
};  
SessionConfig sess1_cfg{  
    .session_name = "sess1",  
    .password = "password1",  
    .company_id = funx::CompanyId{1},  
    .port = funx::TcpPort{20001},  
};  
GatewayConfig cfg{  
    .unique_id = 0,  
    .server_ip4 = "127.0.0.1",  
    .matching_services = { matching_service.getMatchingServiceConfig() },  
    .sessions = {sess0_cfg, sess1_cfg},  
};

Gateway gateway(cfg);

Testing becomes much cleaner when you can create mocks of your components with just a few lines of declarative code.

Reusable Mocks

For services that get used by other services’ tests, they expose a public test library that includes a ready-to-go mock in a mock.h file.

For example, the gateway tests spin up a mock matching service as follows: 

TEST_CASE("Test Gateway One Matching Service", "[gateway]")  
{  
    funx::match::test::RunMockMatchingService matching_service;  
    ...  
    GatewayConfig cfg{  
        ...  
        .matching_services = { matching_service.getMatchingServiceConfig() },  
    };

By default, the mock matching service adds a few test products and runs the matching service in a thread for up to 5 seconds. Furthermore, the mock matching service makes its associated MatchingService::Config readily available so that we can compose it into a GatewayConfig and spin up a Gateway to test.

Catch2 Testing Framework

I prefer the Catch2 testing framework for its focus on code readability and maintainability. I highly recommend Catch2 to anyone writing C++ code.

Sections

Catch lets you structure your tests with sections surrounded by reusable setup and teardown code. Take the following code that tests various rejects for orders: 

TEST_CASE("Test Gateway One Matching Service", "[gateway]")  
{  
    funx::match::test::RunMockMatchingService matching_service;  
    ...  
    Gateway gateway(cfg);  
    ...  
    GatewayTestClient sess0(Client::Config{  
        .gateway_cfg = cfg,  
        .session_cfg = cfg.sessions[0],  
    });

    SECTION("Send order and get reject") {  
        flop::NewOrder new_order{  
            .product = 1,  
            .side = flop::Side::Sell,  
            .qty = 123,  
            .price = 456,  
            .duration = flop::Duration::Day,  
            .client_order_id = 1234567,  
        };

        auto sendAndExpectReject = [&](flop::Reason reason) {  
            sess0.client().sendBasicNewOrder(new_order);  
            auto reject = sess0.requireResponse<flop::OrderReject>();  
            REQUIRE(reject.reason == reason);  
        };

        SECTION("Bad product") {  
            new_order.product = 843578;  
            sendAndExpectReject(flop::Reason::InvalidProduct);  
        }

        SECTION("Bad Side") {  
            new_order.side = static_cast<flop::Side>(255);  
            sendAndExpectReject(flop::Reason::InvalidSide);  
        }

        SECTION("Bad quantity") {  
            new_order.qty = GENERATE(-100, 0);  
            sendAndExpectReject(flop::Reason::InvalidQuantity);  
        }

        SECTION("Bad Duration") {  
            new_order.duration = static_cast<flop::Duration>(255);  
            sendAndExpectReject(flop::Reason::InvalidDuration);  
        }

For every section, Catch starts from the beginning and runs all the higher-scoped setup code. That means for every reject test, Catch creates a fresh matching service, gateway, and test client. We don’t have to worry about state bleeding between tests. More importantly, every section contains precisely the two lines of code relevant to the feature being tested and no extra clutter.

The SECTION macro allows embedding traditional test fixture setup into the flow of the test. Instead of having to jump to wherever the test fixture was defined to check what was already setup, we can just read the tests in a single uninterrupted flow.

Furthermore, every section can add to what the previous scope defined. For example, the “Test Gateway One Matching Service” scope creates the matching service, gateway, and client. The “Send order and get reject” section adds a new_order variable that will be used in all the reject tests. This same new_order variable is not visible to any tests outside the “Send order and get reject” scope. You can’t achieve this level of tidiness with traditional test fixtures.

GENERATE Macro

Catch also makes it extremely easy to vary the value for a given variable. In the prior code snippet, we had 

SECTION("Bad quantity") {  
    new_order.qty = GENERATE(-100, 0);  
    sendAndExpectReject(flop::Reason::InvalidQuantity);  
}

Catch will run the test section once with qty = -100 and another time with qty = 0. You can add as many values as you want to the list and it is much cleaner than a traditional test case iterating over a list of values.

Overall Testing Goals

The primary goal of testing is to catch regressions during codebase updates. However, you also need your tests to be readable and maintainable. Designing your components with testing in mind, and leveraging a testing framework geared towards readability are additional important concepts for a high-quality codebase.

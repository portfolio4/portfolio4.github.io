Modern C++ Design Decisions

This article explains C++ techniques I use to make ownership, state, configuration, and error handling easier to reason about. These choices reflect my personal preferences for writing effective C++. When contributing to an established codebase, I follow the team’s conventions and adapt to its style.

Designated Initializers and Aggregate Types

For passive data structures without constructor-enforced invariants, I often use aggregate types and designated initializers. This makes long lists of fields easier to follow.

Suppose I initialize a transaction via a constructor like this: 

funx::transaction::Transaction(  
    match.product,  
    match.qty,  
    match.price,  
    match.txid,  
    match.seller_company,  
    match.buyer_company  
)

There is a mistake above, where seller_company and buyer_company are accidentally swapped, but it’s not clear from the local code at all. On the other hand, if I initialize it as 

funx::transaction::Transaction{  
    .product = match.product,  
    .qty = match.qty,  
    .price = match.price,  
    .txid = match.txid,  
    .buyerId = match.seller_company,  
    .sellerId = match.buyer_company,  
}

then the mistake becomes obvious to the reader.

Config Structs

I use Config structs for configurable service components: 

struct Config  
{  
    funx::TcpPort server_port;  
};

TcpServerSocket(Config const& c);

The first benefit is that you can use designated initializers when constructing the class to make the code clearer: 

funx::TcpServerSocket server_socket_(funx::TcpServerSocket::Config{  
  .server_port = c.port  
})

A Config struct also keeps constructor signatures manageable as options are added. For example, max_clients can be added alongside server_port, and optional settings can have default values. I find this easier to maintain than a growing list of positional parameters.

The third benefit is extensibility. You can add completely independent configuration structs as needed. For example, if you need a server that listens to multiple ports, you can add 

// For servers that need to listen on multiple ports  
struct MultiConfig  
{  
    std::vector<funx::TcpPort> server_ports;  
};

TcpServerSocket(MultiConfig const& c);

This pattern combines constructor-based initialization with named configuration fields, making the call site easier to read.

Immediately Invoked Lambdas

Immediately-invoked lambdas are useful when a value requires multi-step initialization but the temporary state should remain tightly scoped. They also compose well with designated initializers: 

AddOrder{  
    .order = [&]() {  
        auto rtn = buy;  
        rtn.qty = buy.qty - sell1.qty - sell2.qty - sell3.qty;  
        return rtn;  
     }()  
}

This restricts the scope of the temporary rtn variable so that nothing else accidentally accesses it and keeps the initialization logic in the vicinity of where it is being used.

Strong Typing

While strong typing like the following may seem excessive: 

enum class Product : uint64_t {};
enum class TransactionId : uint64_t {};
enum class CompanyId : uint64_t {};
enum class OrderId : uint64_t {};

This lets the type system catch accidental interchange of semantically different identifiers. Suppose you have the following function: 

// Without strong typing  
void myFunc(  
    uint64_t product,  
    uint64_t transactionId,  
    uint64_t companyId,  
    uint64_t orderId)  
{ ... }

// With strong typing  
void myFunc(  
    Product product,  
    TransactionId transactionId,  
    CompanyId companyId,  
    OrderId orderId)
{ ... }

And suppose you accidentally swapped two parameters when calling myFunc: 

myFunc(product, transactionId, orderId, companyId);

With strong typing, this mistake becomes a compile-time error. With raw uint64_t parameters, the same mistake compiles and must instead be detected through testing or runtime behavior.

Exhaustive Enum Switches

For switches intended to exhaustively handle an enum, I omit the default case so compiler warnings can identify unhandled enumerators: 

switch(level)  
{  
case LogLevel::DEBUG:  
    return "DEBUG";  
case LogLevel::INFO:  
    return "INFO";  
case LogLevel::WARN:  
    return "WARN";  
case LogLevel::ERR:  
    return "ERR";  
case LogLevel::CRIT:  
    return "CRIT";  
}  
return "UNK";

With missing-enum-case warnings enabled, omitting the default case lets the compiler flag enum values that the switch does not handle. For example, GCC provides this through -Wswitch. When a new enum value is added, these warnings help identify switches that need updating.

Variants for Tracking States

A variant can represent a state together with the data that is valid in that state. Gateway sessions have three states:

  1. NotConnected is when the client has not yet connected
  2. Connected is when the client has established a TCP session but has not logged in.
  3. Active is when the client has logged in and we need to automatically cancel all their orders if they haven't sent anything in the last 30 seconds.

A suboptimal way to track this is as follows: 

enum State state_ = State::NotConnected; // NotConnected, Connected, or Active  
funx::TcpSession* session_ = nullptr;
funx::Clock::time_point last_msg_time_;

With separate state and session members, the representation must accommodate the absence of a session while disconnected. A nullable TcpSession* can represent that absence, but it leaves the relationship between connection state and session availability to runtime checks. If the pointer owns a heap-allocated session, it also introduces allocation and lifetime-management responsibilities.

With separate state and data members, last_msg_time_ is also accessible while disconnected, even though it is only meaningful in the Active state.

A variant ties the session directly to the states that require it, making those relationships explicit in the type system. The NotConnected state contains no session, while Connected and Active each contain a TcpSession.

If we instead handle the state representation with a variant: 

// No TCP connection established  
struct NotConnected {};

// TCP connection established, but not logged in yet  
struct Connected {  
    funx::TcpSession session;  
};

// Logged in and trading is permitted  
struct Active {  
    funx::TcpSession session;  
    funx::Clock::time_point last_msg_time;  
};

using State = std::variant<  
    NotConnected,  
    Connected,  
    Active  
>;  
State state_ = NotConnected{};

Then when the state is NotConnected, you do not need to provide a TcpSession anymore. And similarly last_msg_time is only accessible in the Active state.

State-specific behavior can then be dispatched with std::visit: 

std::visit(funx::overloaded{  
    [&](Session::NotConnected&) {  
        // client cannot send us new messages if they're not connected  
    },  
    [&](Session::Connected& c) {  
        pollConnectedState(c, now);  
    },  
    [&](Session::Active& a) {  
        pollActiveState(a, now);  
    }  
}, state_);

With the explicit overloads shown here, the visitor must be callable for every state. Adding a state without a matching overload produces a compilation error. Tests still need to verify that each handler performs the correct transitions and actions.

std::expected and Limited Exception Throwing

I limit explicit exception throwing to constructors so that error handling in the main processing loop stays visible in the calling code. Library calls may still throw, so this is a coding convention rather than a guarantee that the application cannot throw exceptions.

For recoverable errors, I use std::expected to return either a value or an error. One extension would be to mark functions returning these results as [[nodiscard]], allowing the compiler to warn when a result is discarded. This does not guarantee that the caller checks the error case. Also, calling .value() on an std::expected containing an error can throw.

Another extension would be to move throwing construction into explicitly named createOrThrow factory functions, making those potentially throwing calls easier to identify.

No Manual Ownership / Deallocation

Application code avoids manual memory ownership. Resource lifetime is expressed through value semantics and RAII-managed library types rather than explicit new/delete or malloc/free pairs. Standard-library containers still allocate dynamically where needed, and performance-sensitive allocations remain visible at the data-structure level—for example, the matching-engine discussion identifies per-order std::list allocation as a candidate for pooling.

Minimal Multithreading

I keep each service single-threaded to reduce debugging complexity while still supporting multiple clients. This avoids shared-memory races between application threads and makes the service logic easier to reason about and test. Timing and message ordering between services still require care.

One important extension is to offload logging to a separate thread pinned to a dedicated CPU core, keeping disk writes out of the fast path. I omitted this to keep the MVP simple. Logging is already abstracted behind an interface, so an asynchronous implementation could use a concurrent queue without changing the calling code.

Templates and Explicit Constraints

I use templates when they express useful shared behavior, while avoiding metaprogramming that makes ordinary application logic difficult to follow.

Concepts can make generic interfaces clearer by expressing their requirements directly. For example, a binary-protocol helper can be constrained to messages with a price field of the expected type: 

template<typename Msg>  
concept MsgWithPrice = requires(Msg msg) {  
    { msg.price } -> std::same_as<Price&>;   
};

template <MsgWithPrice Msg>  
void operateOnPrice(Msg const& msg) { ... }

My goal is to keep abstractions understandable and make their constraints explicit.

Selective Use of Functional Programming and Ranges

Functional programming and ranges have benefits, but I prefer to use them only when they clearly improve readability over the traditional imperative style. For example, when logging a list of product IDs in human-readable format, I use ranges: 

LOG_INFO("    products=[{}]",  
    cfg.products  
        | std::views::transform([](funx::Product p) {  
            return std::format("{}", p);  
          })  
        | std::views::join_with(std::string(","))  
        | std::ranges::to<std::string>()  
);

I find this pipeline clearly expresses formatting and joining the product IDs. The following loop performs the same task, with explicit handling for the first element: 

std::string product_list_str;  
 if (cfg.products.size() > 0) {  
     product_list_str += std::format("{}", cfg.products[0]);  
 }  
 for (size_t i = 1; i < cfg.products.size(); ++i) {  
     product_list_str += std::format(",{}", cfg.products[i]);  
 }  
 LOG_INFO("    products=[{}]", product_list_str);

I find the loop version less clear because that bookkeeping distracts from the operation being expressed.

In general, I prioritize the form that makes the operation easiest to understand and maintain.

C++ Best Practices

C++ is a great language when you use it effectively. In this article, I’ll point out details that make my C++ code robust.

Table of Contents

Designated Initializers and Aggregate Types

Whenever possible, I make my structs aggregate types and use designated initializers. Designated initializers make tracking long lists of fields much more manageable.

Suppose I initialize a transaction via a constructor like this: 

funx::transaction::Transaction(  
    match.product,  
    match.qty,  
    match.price,  
    match.txid,  
    match.seller_company,  
    match.buyer_company  
)

There is a mistake above, where seller_company and buyer_company are accidentally swapped, but it’s not clear from the local code at all. On the other hand, if I initialize it as 

funx::transaction::Transaction{  
    .product = match.product,  
    .qty = match.qty,  
    .price = match.price,  
    .txid = match.txid,  
    .buyerId = match.seller_company,  
    .sellerId = match.buyer_company,  
}

then the mistake becomes obvious to the reader.

Config Structs

All my constructors take a Config struct: 

struct Config  
{  
    funx::TcpPort server_port;  
};

TcpServerSocket(Config const& c);

The first benefit is that you can use designated initializers when constructing the class to make the code clearer: 

funx::TcpServerSocket server_socket_(funx::TcpServerSocket::Config{  
  .server_port = c.port  
})

The second benefit is support for arbitrary additional fields without expanding parameter lists. For example, we can add a uint32_t max_clients to the config struct. And if you end up adding tons of new fields, some of which have default values, and others do not, you have to go the config-struct route.

The third benefit is extensibility. Additional configurations can be added as needed. For example, if you need a server that listens to multiple ports, you can add 

// For servers that need to listen on multiple ports  
struct MultiConfig  
{  
    std::vector<funx::TcpPort> server_ports;  
};

TcpServerSocket(MultiConfig const& c);

The config constructor paradigm essentially gets us factory functions with designated initializers. This is also the standard pattern in Golang.

Immediately Invoked Lambdas

I use immediately-invoked lambdas frequently when complicated initialization logic is involved. They are very useful with designated initializers: 

AddOrder{  
    .order = [&]() {  
        auto rtn = buy;  
        rtn.qty = buy.qty - sell1.qty - sell2.qty - sell3.qty;  
        return rtn;  
     }()  
}

This restricts the scope of the temporary rtn variable so that nothing else accidentally accesses it and keeps the initialization logic in the vicinity of where it is being used.

Strong Typing

While strong typing like the following may seem excessive: 

enum Product : uint64_t {};  
enum TransactionId : uint64_t {};  
enum CompanyId : uint64_t {};  
enum OrderId : uint64_t {};

It significantly improves safety and code quality. Suppose you have the following function: 

// Without strong typing  
void myFunc(  
    uint64_t product,  
    uint64_t transactionId,  
    uint64_t companyId,  
    uint64_t orderId)  
{ ... }

// With strong typing  
void myFunc(  
    Product product,  
    TransactionId transactionId,  
    CompanyId companyId,  
    OrderId orderId)
{ ... }

When you invoke the function in another distant code file, you are susceptible to accidentally swapping the parameter order. For example: 

myFunc(product, transactionId, orderId, companyId);

With strong typing, the compiler errors out and catches your mistake. Without strong typing, everything is uint64_t and the compiler will not catch the mistake, leaving you to hope your tests catch the bug.

Switch Statements Without Default Case

It is advantageous to use a switch statement without a default case: 

switch(level)  
{  
case LogLevel::DEBUG:  
    return "DEBUG";  
case LogLevel::INFO:  
    return "INFO";  
case LogLevel::WARN:  
    return "WARN";  
case LogLevel::ERR:  
    return "ERR";  
case LogLevel::CRIT:  
    return "CRIT";  
}  
return "UNK";

When the default case is omitted and your switch statement is accidentally missing a case, the compiler emits a warning. Furthermore, if you add a new enum value in the future, the compiler automatically flags all the locations that have not handled the new enum value, making future maintenance easy.

Variants for Tracking States

Variants can be used as a more-advanced enum. Gateway sessions have three states:

  1. NotConnected is when the client has not yet connected
  2. Connected is when the client has established a TCP session but has not logged in.
  3. Active is when the client has logged in and we need to automatically cancel all their orders if they haven’t sent a heartbeat in the last 30 seconds.

The naive way to track this is as follows: 

enum State state_ = State::NotConnected; // NotConnected, Connected, or Active  
funx::TcpSession session_;  
funx::Clock::time_point last_msg_time_;

One problem is if you are in the NotConnected state, this setup requires you to still have a TcpSession. But you can’t provide a valid TcpSession because the client isn’t connected. So you have to hack up your code and make a dummy TcpSession. (Beginners will use a TcpSession* pointer and allocate an actual TcpSession object on the heap once the client connects. This is much less robust.)

Another less-annoying but valid issue is you have a last_msg_time_ variable lying around that is accessible during the NotConnected state, but it shouldn’t be used.

If we instead handle the state representation with a variant: 

// No TCP connection established  
struct NotConnected {};

// TCP connection established, but not logged in yet  
struct Connected {  
    funx::TcpSession session;  
};

// Logged in and trading is permitted  
struct Active {  
    funx::TcpSession session;  
    funx::Clock::time_point last_msg_time;  
};

using State = std::variant<  
    NotConnected,  
    Connected,  
    Active  
>;  
State state_ = NotConnected{};

Then when the state is NotConnected, you do not need to provide a TcpSession anymore! And similarly last_msg_time is only accessible in the Active state.

Finally, if you want to handle the state, you can call std::visit on a variant 

std::visit(funx::overloaded{  
    [&](Session::NotConnected&) {  
        // client cannot send us new messages if they're not connected  
    },  
    [&](Session::Connected& c) {  
        pollConnectedState(c, now);  
    },  
    [&](Session::Active& a) {  
        pollActiveState(a, now);  
    }  
}, state_);

If you are missing handlers for a state, the compiler will error out. This ensures you never accidentally forget to handle a case.

std::expected and Limited Exception Throwing

When thrown liberally, exceptions make code harder to understand because you have no idea whether something further down the call chain will throw. Therefore, in my codebase, the only places where I throw exceptions are constructors. Once the application starts up and begins the fastpath loop, none of the code I write can directly throw exceptions (calls to libraries might indirectly throw, of course).

To deal with error cases, I use std::expected. A couple extensions that I did not include here: first, we can create another type to inherit from std::expected and mark it as [[nodiscard]]. If we ever forget to check the error case, the compiler will warn us. And second, with minor effort all the constructors that currently throw exceptions can be refactored into createOrThrow factory functions that make it even more obvious the call might throw.

Absence of New/Malloc

Throughout the entire codebase, I never explicitly allocate heap memory. There are no calls to new, malloc, make_unique, or make_shared. All the code I directly wrote uses stack-allocated memory. This eliminates the possibility of memory leaks in my code. Of course, the libraries I import use heap memory, but those are open-source, well-vetted, and well-tested.

Minimal Multithreading

Avoid multi-threading where possible to minimize debugging complexity. All the production code is intentionally single-threaded by design (each service is capable of handling many clients though!). Once the logic becomes single-threaded, it becomes deterministic and extremely straightforward to test. Concurrency bugs are no longer possible.

One important extension is to offload all your logging to a separate thread bound to a separate CPU. That way you don’t have disk writes in your fastpath. I skipped this for simplicity and this being a mock project. I did abstract all the logging behind an interface and it would be straightforward to refactor the implementation to offload to a different thread via a concurrent queue.

Minimal Template Metaprogramming, SFINAE, Concepts

I generally try to avoid template metaprogramming and SFINAE. In my opinion, it makes code difficult to understand and maintain.

I find it sometimes acceptable to use SFINAE and Concepts when dealing with binary protocols. For example, many messages in a protocol might all have a field price and you might want to define a function that operates solely on messages with a price: 

template<typename Msg>  
concept MsgWithPrice = requires(Msg msg) {  
    { msg.price } -> std::same_as<Price&>;   
};

template <MsgWithPrice Msg>  
void operateOnPrice(Msg msg) { ... }

Overall, it is best to keep complex template operations to a minimum.

Minimal Functional Programming and Ranges

Functional programming and ranges have benefits, but I prefer to use them only when they clearly improve readability over the traditional imperative style. For example, when logging a list of product IDs in human-readable format, I use ranges: 

LOG_INFO("    products=[{}]",  
    cfg.products  
        | std::views::transform([](funx::Product p) {  
            return std::format("{}", p);  
          })  
        | std::views::join_with(std::string(","))  
        | std::ranges::to<std::string>()  
);

It’s more concise and obvious compared to a traditional C++ for loop where we explicitly have special handling for element 0: 

std::string product_list_str;  
 if (cfg.products.size() > 0) {  
     product_list_str += std::format("{}", cfg.products[0]);  
 }  
 for (size_t i = 1; i < cfg.products.size(); ++i) {  
     product_list_str += std::format(",{}", cfg.products[i]);  
 }  
 LOG_INFO("    products=[{}]", product_list_str);

However, in my experience, using ranges and functional programming for complex logic gets hairy when the logic you’re trying to accomplish doesn’t fit perfectly into the continuation functions that are available. In these situations, it is better to stick with traditional imperative programming.

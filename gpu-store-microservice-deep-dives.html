Database

For simplicity, our database is implemented as a simple log-append file. Every time a new trade occurs, we append to the end of the file. Here’s the relevant code: 

std::expected<void, funx::transaction::proto::ErrorCode>
FileStorage::save(funx::transaction::Transaction const& tx)
{
    FUNX_TRY_VOID(saveInMemory(tx));
    uint16_t size = sizeof(tx);
    ofs_.write(reinterpret_cast<const char*>(&size), sizeof(size));
    auto writeSizeFailed = ofs_.fail();
    ofs_.write(reinterpret_cast<const char*>(&tx), sizeof(tx));
    auto writeTxFailed = ofs_.fail();
    if (writeSizeFailed || writeTxFailed) {
        LOG_WARN("Failed to write transaction. "
                    "Manual intervention needed for {}", tx);
        return std::unexpected(funx::transaction::proto::ErrorCode::FileWriteFailed);
    }
    ofs_.flush();
    return {};
}

For every trade, we store the size of the trade data followed by the trade’s binary data. Everything is done in binary to maximize efficiency. If we crash, on restart, we can read the entire file to bootstrap.

Potential Extensions

To ensure resilience against disk failure, the log can be segmented and backed up to S3.

Finally, everything is hidden behind an API, so we can swap this log-append file for an off-the-shelf database solution at any point.

Matching Engine

The matching engine implements a standard price-time priority algorithm.

We have an Order data structure containing info about each order: 

struct [[gnu::packed]] Order
{
    funx::Product product;
    funx::Quantity qty;
    funx::Price price;
    funx::Side side;
    funx::Duration duration;
    funx::CompanyId company;
    funx::OrderId order_id;

    bool operator==(Order const& other) const = default;
};

Next, every price level is a linked list of orders: 

struct Level
{
    std::list<Order> orders;
    using iterator = decltype(orders)::iterator;
};

When orders trade, we pop from the front in O(1). When orders get added, we push to the back in O(1).

When orders get cancelled, we keep a hashmap of order ID to the order’s iterator and remove from the list in O(1). 

struct OrderData {
    decltype(levels_)::iterator iter_to_level;
    Level::iterator iter_to_order;
};
std::unordered_map<funx::OrderId, OrderData> order_map_;

Every book side is a tree of price levels for log(N) find, insert, and delete operations. And finally, each book has two book sides: buy and sell. 

class BookSide
{
private:
    ...
    std::map<funx::Price, Level, Comparator> levels_;
};

impl::BookSide<funx::BuyComparator> buys_;
impl::BookSide<funx::SellComparator> sells_;

Potential Extensions

We keep things simple and don’t prematurely optimize. But if we’re willing to increase the complexity of the system, there’s lots of possible optimizations.

Memory Pools and Cache Locality

When a new order comes in, we currently append to the level linked list, which does a heap allocation. Instead, we can preallocate a giant memory pool of orders.

You could further improve cache locality by preallocating memory pools for each price level to improve cache locality because orders within a price level tend to be accessed together.

absl::flat_hash_map

We use an std::unordered_map which implements separate chaining. It has bad cache locality so the performance is worse than open addressing solutions like abseil’s flat_hash_map.

The FPGA Misconception

Finally, one misconception to address: moving to an FPGA because it’s “faster”. FPGA clock rates are hundreds of MHz. CPU clock rates are GHz. For a sequential FIFO matching engine algorithm, the FPGA is unlikely to make up the 10x slower clock rate with parallelism. People use FPGAs for a more-nuanced technical reason that I intentionally leave out here. FPGAs are probably not the best platform for your matching engine, but they can be useful in other parts of the infrastructure.

Gateway

Our next microservice is the gateway.

The gateway is simply a translation layer between the user and the matching engine. A single gateway consists of N sessions where each session acts as a TCP server that accepts one client: 

class Gateway
{
    ...
private:
    std::vector<Session> sessions_;
};

Within each session, it’s just tedious state management for that client: 

class Session
{
public:
    // No TCP connection established
    struct NotConnected {};

    // TCP connection established, but not logged in yet
    struct Connected {
        funx::TcpSession session;
    };

    // Logged in and trading is permitted
    struct Active {
        funx::TcpSession session;
        funx::Clock::time_point last_msg_time;
    };

    using State = std::variant<
        NotConnected,
        Connected,
        Active
    >;
    ...
};

Every time the client sends us a FLOP request, we have to translate the request to something the matching engine understands. And every time the matching engine updates us about an order, we have to send the corresponding FLOP message(s) to the client. I’ll have a later C++ deep dive to illustrate techniques we use to keep the code maintainable.

Potential Extensions

The notable missing feature is recovery: both if the client crashes or if the gateway crashes. It’s a tedious feature to code, but a quick-and-dirty implementation would be an append-only log like we have with the database microservice.

Market Data

Our final microservice is the market data service, which is another translation layer between matching engine and user.

A market data server provides 2 UDP multicast channels: incremental and snapshot. 

class MarketDataService
{
    ...
private:
    funx::UdpSocket incremental_socket_;
    funx::UdpSocket snapshot_socket_;
};

We use UDP multicast to disseminate identical data to many consumers. This is significantly more efficient than a TCP session for every client.

To help with clients losing packets, we run redundant market data services broadcasting the same data on multiple multicast channels. The client arbitrates N of these channels.

Potential Extensions

If we had to, we could create a TCP service for clients to request specific sequence numbers.

Time to Market

The design prioritizes simplicity to minimize time-to-market.

I left out a lot of important, advanced features, but was able to build the MVP in 1.5 months, coding 12 or so hours each Saturday and Sunday.

In a work environment with meetings and other responsibilities, I estimate this would’ve taken about a month.

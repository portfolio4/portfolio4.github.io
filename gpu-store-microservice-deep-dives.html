GPU Store Architecture Deep Dive

GPU Store separates order matching, client sessions, market-data distribution, and transaction storage into distinct services. This article explains their responsibilities and the implementation choices in the MVP.

Table of Contents

Database

For the MVP, transaction persistence is implemented as an append-only binary log. Every time a new trade occurs, we append to the end of the file. Here’s the relevant code: 

std::expected<void, funx::transaction::proto::ErrorCode>
FileStorage::save(funx::transaction::Transaction const& tx)
{
    FUNX_TRY_VOID(saveInMemory(tx));
    uint16_t size = sizeof(tx);
    ofs_.write(reinterpret_cast<const char*>(&size), sizeof(size));
    auto writeSizeFailed = ofs_.fail();
    ofs_.write(reinterpret_cast<const char*>(&tx), sizeof(tx));
    auto writeTxFailed = ofs_.fail();
    if (writeSizeFailed || writeTxFailed) {
        LOG_WARN("Failed to write transaction. "
                    "Manual intervention needed for {}", tx);
        return std::unexpected(funx::transaction::proto::ErrorCode::FileWriteFailed);
    }
    ofs_.flush();
    return {};
}

For each trade, the log stores the record size followed by the transaction's binary representation. On restart, the service can replay the log to reconstruct its in-memory state.

Potential Extensions

For durability beyond a single host, log segments could be replicated or asynchronously copied to remote object storage.

The storage implementation is isolated behind an API, keeping the option of adopting an off-the-shelf database without exposing storage details throughout the application.

Matching Engine

The matching engine implements a standard price-time priority algorithm.

Each order is represented by the following strongly typed structure: 

struct [[gnu::packed]] Order
{
    funx::Product product;
    funx::Quantity qty;
    funx::Price price;
    funx::Side side;
    funx::Duration duration;
    funx::CompanyId company;
    funx::OrderId order_id;

    bool operator==(Order const& other) const = default;
};

(Order uses a packed layout because it is also transmitted over the wire protocol. The MVP shares this representation between communication and internal processing. A possible extension is to separate the wire representation from a naturally aligned internal type.)

Next, every price level is a linked list of orders: 

struct Level
{
    std::list<Order> orders;
    using iterator = decltype(orders)::iterator;
};

Within a price level, matching proceeds from the front of the list. A partially filled resting order remains at the front with its remaining quantity; a fully filled order is removed in O(1). New resting orders are appended to the back in O(1).

When orders get cancelled, we use a hash map from order ID to the order’s iterator. Lookup is O(1) on average, and removing the order from the linked list is O(1). 

struct OrderData {
    decltype(levels_)::iterator iter_to_level;
    Level::iterator iter_to_order;
};
std::unordered_map<funx::OrderId, OrderData> order_map_;

Each book side stores price levels in a tree, supporting O(log N) lookup and insertion, where N is the number of price levels. Each book has two sides: buy and sell. Matching an incoming order may involve processing multiple resting orders. 

class BookSide
{
private:
    ...
    std::map<funx::Price, Level, Comparator> levels_;
};

impl::BookSide<funx::BuyComparator> buys_;
impl::BookSide<funx::SellComparator> sells_;

Potential Extensions

The MVP uses standard containers to keep the implementation clear. Further optimization could target allocation behavior and memory locality, with additional implementation complexity.

Memory Pools and Cache Locality

Adding a resting order to the linked list currently allocates a node. A possible extension is a preallocated pool of order nodes to reduce allocation work during order processing. Its capacity and exhaustion behavior would need to be defined.

Grouping order nodes by price level could improve locality because matching accesses orders within a level together. Per-level pools would also need to accommodate uneven order counts across price levels.

absl::flat_hash_map

We use std::unordered_map, whose typical node-based implementation has poorer cache locality than an open-addressing container. Its performance is expected to be worse than alternatives such as Abseil’s flat_hash_map.

Gateway

The gateway translates between the client-facing protocol and the matching engine while managing client sessions. A gateway contains N sessions; in this implementation, each session listens for one client connection: 

class Gateway
{
    ...
private:
    std::vector<Session> sessions_;
};

Each session explicitly tracks whether the client is disconnected, connected but not logged in, or active: 

class Session
{
public:
    // No TCP connection established
    struct NotConnected {};

    // TCP connection established, but not logged in yet
    struct Connected {
        funx::TcpSession session;
    };

    // Logged in and trading is permitted
    struct Active {
        funx::TcpSession session;
        funx::Clock::time_point last_msg_time;
    };

    using State = std::variant<
        NotConnected,
        Connected,
        Active
    >;
    ...
};

The gateway converts requests from the client-facing FLOP protocol into matching-engine requests and translates order updates back into FLOP responses for the client. The Modern C++ Design Decisions and C++ Testing Design articles illustrate techniques we use to keep the code maintainable.

Potential Extensions

The primary omitted production feature is session recovery after either client or gateway failure. A good design would persist sufficient session state and outbound sequence information to reconstruct client state after restart.

Market Data

The market-data service publishes matching-engine updates to consumers through incremental and snapshot feeds.

Each market-data publisher provides two UDP multicast channels: an incremental feed and a snapshot feed. 

class MarketDataService
{
    ...
private:
    funx::UdpSocket incremental_socket_;
    funx::UdpSocket snapshot_socket_;
};

We use UDP multicast to distribute the same updates to multiple consumers without sending a separate copy over a TCP connection to each client. This reduces sender-side duplication as the consumer count grows.

Redundant publishers disseminate equivalent sequenced market-data streams over independent multicast channels. Consumers can arbitrate across N feeds; redundancy helps when a packet is missed on one path but received on another, while packets missed on every feed still require recovery.

Potential Extensions

A possible extension is a TCP retransmission service that lets clients request missing messages by sequence number.

Time to Market

The MVP intentionally prioritizes architectural clarity and implementation speed over production completeness.

I built the MVP over approximately six weekends while intentionally omitting production features such as full recovery and production-grade latency tuning.
